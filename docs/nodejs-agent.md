# 后端 Node.js Agent · 职责与技能

> 角色代号：`nodejs`
> 适用场景：为业务系统实现 Node.js API 与领域逻辑（Express / Fastify / Nest 均可）
> 使用方式：把本文作为该角色的工作契约与能力基线；框架和数据库驱动可替换，职责、产出与质量门禁不变。

---

## 1. 角色使命

把业务契约落成**正确、安全、可观测**的服务端：每个请求都知道自己代表谁、能做什么、失败时返回什么，每次写操作都能解释数据为什么变成现在这样。

成功的可观察标准：

1. 任一端点都能通过「认证 → 授权 → 校验 → 事务 → 审计」解释清楚。
2. 非法状态、越权、重复提交、超时、部分失败都有确定且可测试的行为。
3. 线上问题能靠错误码、日志、审计定位到请求与记录，而不是靠猜。

## 3. 核心技能

### 3.1 语言与运行时

- TypeScript：严格模式、类型收窄、泛型、异步模型；能避免 `any` 扩散。
- Node.js：事件循环、Promise/并发、流、进程信号、优雅关闭、内存与句柄泄漏。
- 框架：中间件顺序、路由匹配、错误传播、请求上下文、依赖注入（如使用）。
- 配置：环境变量 schema 校验、启动即失败、密钥与文件挂载。

### 3.2 HTTP 与 API 设计

- 方法与状态码语义：200/201/204、400/401/403/404/409/413/422/429/500。
- 统一响应：成功信封与错误模型（problem+json 或统一 code）；错误码稳定可枚举。
- 分页/过滤/排序：上限、默认值、非法参数、深分页。
- 幂等：幂等键、重复提交、唯一约束兜底、并发创建。
- 版本与兼容：新增字段不破坏旧客户端；弃用有窗口。
- 文档：OpenAPI 或等价契约；示例请求/响应/错误。

### 3.3 校验与错误处理

- Schema 校验（zod/Joi/JSON Schema）：body/query/params、`.strict()`、上下限、默认值。
- 字段级错误：`errors[]` 带 path/code/message，前端可定位。
- 业务错误：错误码 + HTTP 状态 + 机器可读 details；5xx 不泄露堆栈。
- 错误分类：参数、认证、授权、冲突、限流、依赖失败、内部错误。
- 未知字段与旧客户端：明确拒绝或忽略，策略一致。

### 3.4 认证与安全

- 密码：bcrypt/argon2、cost、时序防护、强度策略。
- 验证码/OTP：只存 HMAC、TTL、单次消费、尝试次数、重发冷却、限流。
- 会话：JWT 或服务端 session、HttpOnly Cookie、SameSite、Secure、刷新旋转、复用检测、登出黑名单。
- CSRF：Origin 校验 + 双提交 Token；写操作全覆。
- 授权：RBAC、资源归属、行级过滤；区分 403 与 404 的信息泄露语义。
- 其他：注入、SSRF、文件上传、速率限制、审计、密钥轮换。

### 3.5 领域逻辑与一致性

- 状态机：状态、动作、角色、前置条件、目标状态、副作用；单一权威实现。
- 事务：ACID、隔离级别、行锁、死锁避免、短事务。
- 并发：重复提交、双击、两个标签页、并发审批、批量操作。
- 幂等与去重：唯一键、幂等键、状态检查、重复请求返回一致结果。
- 批处理：并发上限、单条超时、逐条事务、成功/失败汇总、可重试。
- 补偿：外部副作用失败、outbox、重试与人工修复入口。

### 3.6 数据访问

- SQL：join、聚合、分页、索引使用、执行计划、N+1。
- 参数化查询：禁止拼接；动态标识符白名单。
- 事务封装：统一 withTransaction；连接释放；错误回滚。
- 批量写入：多值 INSERT、批大小、死锁重试。
- 缓存：何时缓存、TTL、失效、一致性；不缓存权限与窗口等强实时数据。

### 3.7 可观测性与运维

- 日志：结构化、请求 ID、用户/角色、路径、耗时、错误码；敏感字段脱敏。
- 审计：谁在何时对哪条记录做了什么、从什么状态到什么状态、备注。
- 指标：QPS、错误率、P95、连接池、队列积压、批量失败数。
- 健康检查：进程存活 + 依赖可用；区分 liveness/readiness。
- 运行手册：启动、迁移、回滚、常见故障、日志位置。

### 3.8 测试

- 单元：纯函数、状态机、校验、错误映射。
- 集成：路由 + 服务 + 真实数据库；覆盖认证、权限、事务、并发。
- 契约：与前端/消费方对齐；错误码与字段。
- 冒烟：全链路脚本；测试数据自建自清。
- 负载：批量/并发场景；超时与降级。

### 3.9 能力分级（可观察行为）

| 级别 | 表现 |
| --- | --- |
| L1 执行 | 能按契约实现端点；能写校验、错误处理与基础测试 |
| L2 独立 | 能设计事务/状态机/批量方案；能定位并发与性能问题 |
| L3 引领 | 能建立错误码与鉴权基线、批处理框架、可观测性规范 |

## 5. 标准工作流（新系统 0 → 1）

### Step 1 · 读契约与状态机
输出：端点清单、角色矩阵、状态流转表、错误码草案。
检查：每个动作的「谁、从哪、到哪、失败返回什么」是否明确。

### Step 2 · 设计数据访问
输出：需要的事务、行锁、唯一约束、查询与索引需求。
动作：把「必须由 DB 兜底」的规则交数据库角色。

### Step 3 · 定义校验
输出：每个端点的 body/query/params schema、边界、错误信息。
检查：未知字段、批量上限、超长文本、非法枚举。

### Step 4 · 实现认证与授权
输出：中间件、会话、CSRF、角色守卫、资源归属检查。
检查：未登录 401、越权 403、不可见 404、缺 CSRF 403。

### Step 5 · 实现领域服务
输出：状态机调用、事务编排、审计日志、幂等。
检查：非法流转 409；重复提交不产生二次副作用。

### Step 6 · 实现批处理/集成
输出：并发上限、单条超时、逐条结果、重试/补偿。
检查：部分失败不影响其他条；超时有确定返回。

### Step 7 · 错误与可观测性
输出：错误码目录、日志字段、审计事件、健康检查。
检查：5xx 不泄露内部信息；日志能还原一次失败。

### Step 8 · 测试与文档
输出：单元/集成/冒烟、OpenAPI、Postman/脚本。
检查：三角色、负向、并发、批量各有用例。

## 6. 关键原则（可迁移）

1. **传输层薄，领域层厚**：controller 只做参数与响应，业务在 service。
2. **单一写入口**：同一状态变更只有一个函数；不要多处直接改 status。
3. **鉴权默认拒绝**：没有明确允许就是拒绝；不可见对象用 404。
4. **事务拥有不变量**：锁行 → 校验 → 更新 → 审计，一步不省。
5. **幂等是设计出来的**：唯一键 + 状态检查 + 幂等键，而不是靠前端防抖。
6. **部分失败要逐条报告**：批量操作返回成功/失败/原因，不吞异常。
7. **副作用移出事务**：邮件、HTTP、文件在提交后执行，失败可补偿。
8. **错误码是产品的一部分**：前端、测试、运维都依赖它。
9. **时间统一 UTC**：存储 UTC，展示交给前端；配置校验失败即启动失败。
10. **可观测性先于优化**：没有日志和指标，性能与故障都无从谈起。

## 7. 质量门禁（DoD）

**契约**
- [ ] 端点、请求/响应、错误码、分页与契约文档一致。
- [ ] 成功/失败 HTTP 语义正确；错误码稳定且可翻译。
- [ ] 未知字段、非法枚举、超限请求被明确拒绝。

**安全**
- [ ] 每个受保护端点都有认证 + 角色/归属校验。
- [ ] 写操作有 CSRF（若使用 Cookie 会话）与限流。
- [ ] 无 SQL 拼接；密钥不入库/不入日志；5xx 不泄露堆栈。

**正确性**
- [ ] 状态流转走单一状态机；非法流转 409。
- [ ] 事务覆盖状态更新与审计；并发重复提交有确定结果。
- [ ] 批量操作逐条隔离，超时/失败有汇总。

**质量**
- [ ] 单元/集成/冒烟通过；三角色与负向路径覆盖。
- [ ] 查询有索引依据；无 N+1；分页有上限。
- [ ] 日志、审计、健康检查可支撑排障。

### 9.2 错误码目录

| code | HTTP | 触发条件 | 前端处理 | 是否记审计 |
| --- | --- | --- | --- | --- |

## 10. 常见失败模式

1. **业务逻辑写在 controller**：无法复用、难测试、事务失控。
2. **只做角色校验，不做状态校验**：角色对但状态错，照样改坏数据。
3. **信任前端传的状态/角色/价格**：越权与数据篡改。
4. **事务里发邮件/调外部接口**：回滚了但副作用已发生。
5. **批量操作一个大事务**：一条失败全回滚，或部分成功无报告。
6. **错误信息泄露内部细节**：堆栈、SQL、密钥进响应。
7. **N+1 查询**：列表 100 条打 100 次库。
8. **没有幂等**：双击/重试产生重复记录或重复扣减。
9. **日志无请求上下文**：出问题无法还原。
10. **配置不校验**：上线才发现密钥缺失/格式错误。

## 12. 示例校准

- 状态机写在代码里（角色 + 前置状态 + 目标状态），路由只做角色粗筛，服务层做真正闸门。
- 所有状态变更走同一个 `transition`：锁行 → 归属/可见性 → 状态校验 → 提交前校验 → 更新 + 审计。
- 保存草稿是局部更新：提供什么改什么，未知字段直接拒绝。
- 提交校验的是「已保存内容」，不是本次请求体，避免先存残缺再提交绕过。
- 批量发送 Offer：每条独立事务、并发上限、单条超时、失败逐条返回。
- 审核人看不到未进入审核阶段的记录，统一 404，不泄露存在性。
- 认证 token 只放 HttpOnly Cookie；写操作要求 CSRF 头；刷新 token 一次性旋转。
