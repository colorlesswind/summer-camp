# ADR-0001：模块化单体，按业务域分目录

- 状态：Accepted（2026-11-22 回溯补录，依据代码基线 `0a63c1e`）
- 涉及区域：`server/src/**`

## 背景

系统包含三条角色链（学生 / 管理员 / 导师）和两类核心能力（认证、申请流转），
单次状态流转需要「申请记录 + 名额 + 状态日志」在同一事务内完成。
团队规模小、交付周期短，没有独立扩缩容或独立发布的需求。

## 选项

| 选项 | 代价 |
| --- | --- |
| A 按技术层全局分层（controllers / services / repositories） | 一个业务改动横跨多个目录，边界靠记忆维持 |
| B 模块化单体，按业务域分目录 | 域间共享事务简单；域边界需要纪律约束 |
| C 拆微服务（认证 / 申请） | 状态 + 名额的强一致事务需要分布式方案，成本远超收益 |

## 决策

采用 B：每个业务域自成一个目录，内部含 controller / service / repository / routes / schema / types；
跨域只共享 `common/`、`infra/`、`middleware/`、`db/`、`config/`。

## 理由

- 申请流转与名额必须同事务，单体是成本最低的正确实现。
- 按业务能力（而非技术层）切分，新增需求通常只落在一个域内。
- 模块边界在目录层面可见，评审时容易发现「跨域直接查表」的越界。

## 后果

- 新增业务域 = 新建目录 + 在 `server/src/routes.ts` 挂载，不改其他域的代码。
- 域间只能通过 service 公开方法协作，禁止绕过服务层直接操作别域的表。
- 若要拆服务，需先把域内 repository 抽成接口，按调用点迁移；当前不做预留抽象。

## 回滚

若未来必须拆分：先冻结域间同步调用点 → 抽出仓储接口 → 按域逐个迁移 →
最后移除同库跨域事务。拆分前必须为跨域不变量补契约测试。

## 证据

| 位置 | 说明 |
| --- | --- |
| `server/src/routes.ts` | 业务模块统一在根路由挂载（`/user`、`/form`） |
| `server/src/app.ts` | 中间件与错误处理只装配一次，与业务域解耦 |
| `server/src/user/**`、`server/src/form/**` | 各域自带 controller / service / repository / routes / schema |
| `server/src/{common,infra,middleware,db,config}` | 跨域共享能力 |
